// Selected Work

Per-org Login Architecture

Toddle · 2023–2024

Toddle had one global login page serving every school. As we added SSO providers, the page got crowded — and every new provider for an existing school still required an engineer to flip a flag in the database. We needed per-org login pages that could scale with the SSO catalogue, gate access at the org level (so disabling a method for a school actually disabled it, even on the global URL), and stay performant across 500+ organisations running mixes of Google, Microsoft, and custom IdPs.

We shipped a per-org login surface that admins configure themselves, with method-level allowlisting enforced server-side regardless of which login URL a user hits. The global page still works for orgs that prefer it.

Impact — Eliminated a recurring manual-ticket workflow that was consuming ~15 engineer-hours/month across the org base; SSO enablement went from a ticket queue measured in hours to a self-serve toggle measured in seconds.

What I’d redo — The admin-side setup UX. The architecture is solid, but a first-time admin without docs has to think harder than they should. Information design over engineering on the next pass.

Generic SAML & OAuth Integration

Toddle · 2023–2024

Before this work, Toddle’s “SSO” meant Google or Microsoft OAuth. Anything else was a one-off engineering project. Schools running Okta, Azure AD via SAML, ADFS, or any other standards-compliant IdP were stuck. We built generic SAML and OAuth integration paths that admins configure end-to-end without engineering involvement, working against any compliant provider.

The integration handles the parts that are easy to get subtly wrong: signature validation, clock-skew tolerance, NameID handling, attribute mapping, and the edge cases that only appear when you talk to real-world IdPs.

Impact — Moved Toddle from two hardcoded IdPs to any standards-compliant SAML or OAuth provider, configured by admins without engineering involvement. Removed identity integration as a procurement blocker for enterprise-tier customers.

What I’d redo — The SAML library choice. It works, but its abstractions leak in places I’d rather they didn’t and the docs are thin. The alternatives at the time weren’t better — that doesn’t make me happier about the dependency. The admin UX has the same first-time-user gap as the per-org login work.

Self-serve Client Onboarding

Toddle · 2022–2023

Onboarding a new school meant migrating student, staff, parent, and class data from their SIS into Toddle — and previously, that meant an engineer running database updates by hand, often with several rounds of back-and-forth with the school to fix data shape issues. Slow for the school, expensive for engineering, a bottleneck on growth.

I worked on a self-serve rostering module: schools configure their own migration, monitor progress, control settings, and (with a later cron-based optimisation I was part of) opt into automatic recurring sync. PRD, scoping, UX, and implementation were all in scope.

Impact — Removed developer-in-the-loop from the rostering happy path. New schools onboard themselves; engineering only gets pulled in for genuinely unusual source-data shapes.

What I’d redo — Honestly, less than I’d like — later design iterations haven’t found a meaningfully simpler shape. That’s either a good sign or a sign I should look harder.

Also at Toddle: MFA implementation, a Temporal-based replacement for our long-running task architecture, and a handful of smaller authn/authz pieces along the way.
